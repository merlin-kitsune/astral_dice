# 执行时序 / 触发顺序检查清单(Execution-Order Checklist)

> 用途:审计「相互影响的效果」在**时间轴上的先后、基准与覆盖关系**时,按本清单逐类遍历,避免只看到单个效果的实现而漏掉跨系统的顺序依赖。
> 适用:本仓 `astral_dice_multiloader`(neoforge-1.21.1 + forge-1.20.1,双版本必须并排核对)。
> 配套:总报告 `docs/interaction-audit-1.2.1.md`(第一次全量扫描)、切片 `docs/audit-slices/S*.md`。
> **纪律(每条结论都必须满足)**:①证据 = `文件:行号` + 代码**原文**(反编译源码/字节码要标注来源);②不可达路径**不得**列为缺陷;③每条给「最小实机可区分步骤」;④判定分级 = 证实 / 修正 / 证伪 / 未核验;⑤单侧(只在一个版本存在)差异单列。

---

## 0. 怎么用

1. 先画**领域表**:参与方(卡牌/筹码/立牌/骰子/事件/资源池)→ 触发点(事件阶段 + 优先级)→ 它写入什么(数值/状态/计时器)。
2. 对每个"写入方"问三件事:**谁先谁后有没有契约**、**基准是什么**、**会不会被后写者覆盖**。
3. 只保留"两个以上系统对同一载体(同一附件/同一事件/同一属性)写入"的交叉点——那才是时序缺陷的温床。
4. 用第 I 节的形式落盘结论。

## A. 事件阶段与优先级

| # | 检查点 | 判据 / 症状 | 证据要求 |
|---|---|---|---|
| A1 | **事件阶段映射跨版本等价** | 先画阶段表再谈顺序。1.21.1 `LivingIncomingDamageEvent`(减伤前,可取消)↔ 1.20.1 `LivingAttackEvent`;1.21.1 `LivingDamageEvent.Pre`(护甲+附魔后、**吸收前**)↔ 1.20.1 `LivingDamageEvent`(护甲+附魔+**吸收后**);1.20.1 `LivingHurtEvent`(护甲前)**无 1.21.1 对应**。把 `Pre` 当 `LivingHurtEvent` 的等价物会整体错位 | 反编译 `LivingEntity.java` 的派发行号(1.20.1 约 :1665/:1680;1.21.1 约 :1787/:1789/:1790-1792) |
| A2 | **同优先级多订阅者 = 顺序无契约** | 37 个 `@EventBusSubscriber` 自动注册,顺序 = jar 内 `.class` 条目顺序(加载器 `ModFileScanData.annotations` 的 `LinkedHashSet` + 顺序 `forEach`)。任何"我会先于/晚于别人执行"的隐含假设都是缺陷 | 列出同事件同优先级的全部订阅者;给出"今天安全"的依据(jar 条目索引)并注明**不是契约** |
| A3 | **该显式声明优先级的地方** | 凡是"必须晚于某人"(清理要晚于保命取消)、"必须早于某人"(拦截要先于结算)的逻辑,必须用 `HIGH/HIGHEST/LOW/LOWEST` 表达 | 谁依赖谁 + 当前优先级 + 反转后的后果 |
| A4 | **取消语义** | `setCanceled(true)` 后,后续监听器若检查 `isCanceled()` 则跳过(NeoForge `SubscribeEventListener`、Forge `ASMEventHandler`)。**死亡清理、发奖、状态推进**在动手前都必须检查;反之"保命成功"的路径必须让清理真的被跳过 | 取消者行号 + 每个消费者的 `isCanceled()` 检查行号(缺失处逐一列出) |
| A5 | **嵌套派发与重入** | 在事件处理里再触发同一事件(如嵌套 `hurt`)会重入整条链:需要重入保护(深度计数 / ThreadLocal 门闩 / 显式目标过滤),否则同一效果叠加两次 | 嵌套触发点行号 + 保护机制行号 + 失败时的可观察现象 |
| A6 | **客户端/服务端与 tick 相位** | 双端各自跑一遍、`TickEvent.Phase` 未过滤导致每 tick 跑两次;客户端预测与服务端权威不一致 | 注册点 + 相位/端判定行号 |
| A7 | **同 tick 内多次触发** | 一次攻击/一次死亡可能被多个来源在同 tick 触发多次(`onKill` 多槽位、溅射连锁),去重键必须唯一 | 触发点清单 + 去重实现(签名/窗口) |

## B. 数值修饰器:乘法 / 加法 / 覆盖

| # | 检查点 | 判据 / 症状 | 本仓已证实实例 |
|---|---|---|---|
| B1 | **覆盖式写入丢弃前置修饰** | `setXxx(最终值)` 不读旧值 ⇒ 高优先级已改过的数值被丢 | A3:骰战 `setNewDamage(finalDmg)` 覆盖(`DiceCombatEvents`),末影骰雨中 ×1.4 失效;修法 = 把该修饰注册成骰战因子或受击侧修饰器 |
| B2 | **百分比基准混用** | 同一类减免有三种基准:**基础值**、**当前最大值**、**剩余值**、**常量**。混用 ⇒ 结果取决于"何时算、佩戴了什么" | **枪匠冷却三连**(见 §C2):`命运指引` 取"通用最大值"、`加急加快` 取**常量**一半、`史莱姆` 取**绝对剩余** −10s |
| B3 | **注册/注销成对** | 装备/卸下、buff 到期/移除、死亡/重生 四条路径都要对称注销,否则残留 | 攻防修饰器按名字 `setDefenseArmorBonus(...,0)` 注销;漏一处即残留 |
| B4 | **取整与截断顺序** | 整数除法先后、`min/max` 钳制发生在乘法前还是后,都会改变结果;`ticks/2` 再 `×0.8` 与先 `×0.8` 再 `/2` 在奇数上不同 | 冷却链路 `(base /2)→(×0.8)` |
| B5 | **多来源同类修饰是否被去重** | 用同名 key `set` 而非 `add` ⇒ 后写者覆盖前者;"同一目标每段限一次"类标记要能在正确的时点重置 | 弱点识破的每段奖励标记 |
| B6 | **伤害/数值的"哪一部分"参与修饰** | 加成是并进同一事件(会一起吃护甲/保护)还是单独结算(真伤);单独结算又会被无敌帧吞 | A1:法伤加成走嵌套真伤 ⇒ 被无敌帧差额结算;修法 = 伤害类型打 `bypasses_cooldown` |

## C. 冷却与计时器(本次重点)

| # | 检查点 | 判据 / 症状 | 本仓已证实实例 |
|---|---|---|---|
| C1 | **"开始冷却"入口是否唯一** | 多个入口各自算基准 ⇒ 同一个冷却值取决于走了哪条路 | `SIGN_ACTIVE_COOLDOWN_END` 有 **7 个写入方**(`BaseSignItem`、`DiceCombatEvents` 三处待命释放、`FateGuidanceCardItem`、`KomachiSignItem`、`JasmineSignItem`、`LuluSignItem`、`CurrentCoreChipItem`) |
| C2 | **"最大值"是否取自同一函数** | 存在两条并列的"最大冷却"函数时,消费方各取一条 ⇒ 减免基准与"实际写入的冷却"不一致 | **枪匠(实测)**:`MosesSignItem.signCooldownTicks`(佩戴枪匠时基础 **120s**,再 诡异骰子减半、再充能 −20%)与 `WeirdDiceHandler.signCooldownTicks`(基础 **180s**,同样减半与充能)**并存**。枪匠待命释放走前者(`DiceCombatEvents` moses 分支),其余立牌走后者 |
| C3 | **减免口径:剩余 vs 最大** | 有的按"剩余时间的 30%"(`now + remaining*0.7`,正确),有的按"最大冷却的 50%",有的按"常量的一半",有的按"绝对 −10s"。**减到负数会被 `max(now, ...)` 钳成"立即完成"** | ①`命运指引`:`maxCooldown = WeirdDiceHandler.signCooldownTicks` ⇒ 玩家用**枪匠**开局(实际 120s)时,减免仍按 180s 的一半 = 90s 算 ⇒ 过度减免;②`加急加快`(扫地机被动):`cdEnd - SIGN_ACTIVE_COOLDOWN_TICKS/2` = **固定 90s**,而枪匠+诡异骰子实际只有 60s ⇒ `max(now, ...)` **直接归零 = 免费立即完成**,应为"最大冷却的 50%"却变成"整个冷却重置" |
| C4 | **计时器与状态分离** | 状态(类型枚举)与计时器(到期刻)必须分开:判定只看状态;计时器归零必须**自动重置状态**,且**不依赖载体是否仍在**(立牌/饰品离身后也要能重置) | S6-C2:残留正计时器会让该玩家**任何立牌主动都不再进入冷却**(可无限连发);根因 = 门槛只看 `getSignReadyExpire <= 0` 且超时清除写在立牌自己的 `curioTick` 里 |
| C5 | **陈旧计时器/残留状态** | 绝对值时间戳 `> 0` 被当作"仍在进行中";跨重登保留 | 同上;以及出牌轮计数跨重登残留(A9) |
| C6 | **冷却期间换装/重登/换维度** | 冷却被重置(无冷却可用)或被错误延长 | 玩家级冷却刻意不被装卸重置(设计),但**减免基准随当前装备变化**是缺陷(见 C2/C3) |
| C7 | **冷却作用域 vs 状态作用域** | 哪些是玩家级(立牌主动冷却、出牌轮冷却),哪些是物品级(卡牌耐久);玩家级状态**禁止**被物品装卸回收 | 忍者 +1 出牌数"授予即消耗,装卸不回收"(不变量依据) |
| C8 | **减免的来源与条件是否与文案一致** | tooltip/手册写的减免口径必须能在代码里找到唯一出处;"−50%""−10 秒"要能对上算法 | 修 C3 前先定夺口径,再改文案 |

## E. 饰品(Cuios)装卸五路径

**必须逐路径过一遍:①玩家有意卸下 ②玩家换装(A→B) ③Curios 自身重载(from=to 同一物品) ④由 Curios 自身导致(槽位收缩/死亡掉落) ⑤死亡/重生。**

| # | 检查点 | 判据 / 症状 | 本仓已证实实例 |
|---|---|---|---|
| E1 | **回调参数语义** | Curios `ICurioItem.onEquip(slotContext, prevStack, stack)` / `onUnequip(slotContext, **newStack**, **stack**)`:第 2 参是**将要占用槽位的栈**(真正卸下时 `EMPTY`),第 3 参才是被卸下的饰品 | S6-C1:全仓 4 处把第 2 参当被卸下的物品 ⇒ ①立牌把归零写进了错误的栈(真正卸下时写 `EMPTY`)②`stillInSlot` 误判 ⇒ 换装跳过整段清理 |
| E2 | **"玩家有意" vs "系统导致"** | 只能用 Curios 给的参数区分:`newStack` 非空且与 `stack` 同一物品 = 系统重载(不清理);否则 = 玩家有意(清理) | 同 S6-C1 修法 |
| E3 | **清理函数的入参** | 清理逻辑必须收到**被卸下的那个栈**;写物品组件(数据组件/耐久/NBT)时尤其致命 | `misaki_sign_stacks`/`jasmine_*`/`padman_*` 三个立牌的组件归零 |
| E4 | **全局单例写入** | 对 `ItemStack.EMPTY` 调 `set(...)` 会写进**全局单例**的 `PatchedDataComponentMap`(`ItemStack.EMPTY` 的 `components` 是可变对象) | 同 S6-C1 的连带后果 |
| E5 | **属性修饰器对称性** | 装卸/死亡都要移除,且用稳定标识(UUID/名字) | 各立牌 `setDefenseArmorBonus(...,0)` |
