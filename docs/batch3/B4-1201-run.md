## ⚠️ 为什么没用「全流程 `--version 1.20.1`」

任务描述假定 `--version 1.20.1` 只跑 1.20.1,但读 `mt.ps1` 源码可证**并非如此**:

- `mt.ps1:339` 起的**全流程分支完全忽略 `$Version`**,固定 `foreach ($v in @(Get-MtVersions))` = `1.21.1 → 1.20.1`(顺序见 `lib/Mt.Paths.psm1:29`);
- `mt.ps1:379-383`:1.21.1 未通过 ⇒ `gateOpen=$false` ⇒ **1.20.1 被记 `GATED`,根本不执行**;
- `--version` 只在**单阶段分支**(`mt.ps1:339 if ($Phase)`)与 `stop` 分支生效。

即「`--version 1.20.1` 不会触发 1.21.1 门控」不成立。首轮实测确认:全流程启动后打出 `MT VERSION: 1.21.1` 并开始构建 1.21.1(见 `temp/b4_1201.out.log`),遂在构建阶段即收停,改走任务允许的分步路线(`--phase build/env/launch/cases` 单阶段默认不清理客户端,launch→cases 可共存)。

## FAIL 逐条定性与依据

### ① ENDER-DICE-TOTEM-GLOWING-1.20.1 — **探针缺陷**(产品侧结论:未验证,不能判产品有缺陷)

5 条失败断言(第 19/20/22/23/24 步)全部是「探针行未按预期出现」:

```
[FAIL] 19. assert — /AP_ET_P1_AFTER:marked=0:glow=0:speed=1:.*:bypass=0:fired=1:api=(...)/ 未命中
[FAIL] 20. assert — /AP_ET_P1_OK:1/ 未命中
[FAIL] 22./23./24. assert — P2_AFTER / P2_OK / VERDICT 同上未命中
```

但探针**确实发出了这些行**,原始读数(`run/1.20.1/logs/latest.log`)为:

```
AP_ET_P1_BEFORE:mode=forced_survival:marked=1:glow=1:speed=1:hp=20:alive=1:invul=0:totem_cd_left=-4885
AP_ET_HIT1:src_ex:TypeError: Cannot find function source in object net.minecraft.world.damagesource.DamageSources@70751747.
AP_ET_P1_AFTER:marked=1:glow=1:speed=1:hp=20:alive=1:invul=0:totem_cd_left=-5041:bypass=-2:fired=0:api=n/a
AP_ET_P1_OK:0
AP_ET_P2_AFTER:marked=0:glow=1:speed=1:hp=20:alive=1:invul=0:totem_cd_left=-5271:bypass=-2:fired=0:api=n/a
AP_ET_VERDICT:gated_clear=0:control_keep=0:marked_cleared=1
```

**根因(产品代码从未被执行)**:`hp=20` 全程不变、`fired=0`(保命未触发)、`api=n/a`、`bypass=-2`(仍是 prep 里的哨兵值)= 致死伤害**一次都没打出去**,末影骰的保命分支根本没进入,故 GLOWING 门控行为无任何读数。

具体缺陷位置 = 本次待验证的「C4 致死注入改走直接 Java 调用」那段:

- `scripts/test/resources/kubejs/1.20.1/server_scripts/astral_bugfix_probe.js:3148-3153`
  ```js
  try { src = p.level.damageSources().source(ResourceKey.create(Registries.DAMAGE_TYPE,
                     new ResourceLocation("minecraft:generic"))); }
  catch (e0) { return "src_ex:" + exText(e0); }      // ← 直接 return,后面 6 条路线全被跳过
  ```
  1.20.1 的 KubeJS/Rhino 看不到 `DamageSources#source(ResourceKey)` ⇒ 抛 `TypeError` ⇒ **`return` 提前退出**,连同 `:3165-3173` 的 `fall / damage / kjs_damage / attack / kjs_attack` 与**兜底的原版 `/damage @a 1000 minecraft:generic` 命令**(`:3171`)全部未尝试。这正是 note 第 3 条自称「逐条尝试、任一条生效即停」的路线表未兑现之处。
- **最小复现**:游戏内执行 `/astralprobe` 的 `hit1` ⇒ 日志出现 `AP_ET_HIT1:src_ex:TypeError: Cannot find function source in object ...DamageSources` 且 `bypass=-2:fired=0:api=n/a`。
- **同族旁证**:同一失败模式在别的探针路径也出现 —— `AP_P1_IMM_API:none[damage:TypeError: Cannot find function damage in object ServerPlayer[...]]`(见下条)。即 1.20.1 上 `p.damage(...)`/`DamageSources#source(...)` 这两个 Rhino 入口都不可见,而 `causeFallDamage` 可见且可用(`AP_P1_CTRL_OK:1`)。

**结论**:用例/探针问题(1.20.1 KubeJS API 可见性 + try/catch 提前 return)。**不是**产品缺陷候选;产品侧「带 MARKED 时保命清 GLOWING、无 MARKED 时保留」这一门控**本轮未取得任何读数,应视为未验证**。**未改动任何断言**,也未擅自修探针(该探针正是本批要被验证的对象)。
