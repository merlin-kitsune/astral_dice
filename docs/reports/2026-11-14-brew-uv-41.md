# 仙酿【BREW】几何负尺寸 + 256 UV 修复（26.4-SNAPSHOT.41）

- 日期：2026-11-14
- 版本：`26.4-SNAPSHOT.41`（五线同号）
- 触发：游戏内【仙酿】（`astral_dice:souri_drink`，`Variant=1`）丢失 bbmodel 上的纹路与下半身结构；用户要求按 Blockbench 的负尺寸语义重新导出后再看。

## 症状

- 1.21.1 旧版（`.39`/`.40`）实机只剩一个偏扁的蓝色瓶身，bbmodel 里的金色肩花、腰带、侧面 S 形饰、金色底缘、下半身笼状条带都没有。
- 26.1.2 用正尺寸 + 256 UV 的中间版本时又出现相反结果：瓶身下半部变成金色壳体、蓝色笼状条带包在外面，和 bbmodel 不一致。
- 两线的几何/UV 顶点写入顺序、`fixInvertedFlatCube`、shader（`texCoord0 = UV0`，无纹理矩阵）逐条比对一致，排除 V 翻转与两线渲染通道差异。

## 根因

1. **UV 元数据取错**：bbmodel 的 `resolution` 是 128×128，但 `textures[0]` 的实际 PNG 是 256×256（`uv_width/uv_height`=128，内容只占左上 128×128）。旧生成器把 `resolution` 写进 geo 的 `texture_width/height`，所有 UV 被放大 2 倍，采样到透明区域，180 个 outline 薄壳整片消失。
2. **方块符号被抹掉**：旧生成器用 `abs()`/min/max 把所有 cube 归一成正尺寸。bbmodel 里有 180 个 `*_outline` 方块的 `to-from` 是负的；Blockbench 的 `compileCube` 会保留这个符号并按面重新分配 UV（up/down 面还有一次 UV 翻转）。正尺寸化后物理范围看似相同，但薄壳的面朝向/UV 分配错位，这就是「金壳/蓝笼」互换的来源。

## Blockbench 原生导出语义

`build/tmp-dsh/bb_asar2/bundle.js` 的 `compileCube`（`V6`，offset ≈ 8671629）：

```js
origin = from.slice();
size = cube.size();               // to - from，可负
origin[0] = -(origin[0] + size[0]);
// 有旋转时：
pivot = cube.origin.slice(); pivot[0] *= -1;
rotation[0] *= -1; rotation[1] *= -1;
// 每个面：
uv = [a, b];
uv_size = [c - a, d - b];
// up/down 再执行：
uv[0] += uv_size[0]; uv[1] += uv_size[1];
uv_size[0] *= -1;   uv_size[1] *= -1;
```

新导出 `build/tmp-dsh/gen_signed.py` 严格按上式生成，`texture_width/height` 读 PNG IHDR 的真实 256，而不是 bbmodel 的 `resolution`。

## 结论

- 负尺寸不是「渲染开关」，而是 Blockbench 几何的一部分；必须连符号一起导出，同时把 `texture_width/height` 取实际 PNG 尺寸（256），二者缺一都会丢细节。
- 后续同类 bbmodel 导出统一走 `gen_signed.py` 的语义，不再用正尺寸归一化；自检仍需保持 `winegourd` 逐骨骼一致。
