## 3. 红标根因（两例均为**测试资产与现行产品语义漂移**，非产品缺陷）

### 3.1 CHIP-LOGIC：购买后 5:00 冷却 / 购买即关店

失败断言（原始模式逐字）：

```
AP_CL_CBUY:idx=-1:ex=-:bal=990->990
AP_CL_CBUY:idx=3:ex=-:bal=990->990
AP_CL_CDENY:before=InventoryMenu:after=ChipShopMenu:inv=0/36:all=0
AP_CL_CSEQ5:price=15:purchased=1:refreshes=2/5:owned=1
AP_CL_CSEQ5OWN:0:astral_dice:…_chip:owned=0,1:…:owned=0,2:…:owned=0
AP_CL_CUSE:res=[^:]*:menu=ChipShopMenu
```

证据（游戏日志，两轮独立复现）：

```
[Server thread/INFO] [ChipShopOpener]: [astral_dice] CHIP_SHOP_OPEN_DENIED player=Dev reason=cooldown
[CHAT] AP_CL_CBUY:menu=null
[CHAT] AP_CL_CUSE:res=CONSUME:menu=InventoryMenu
```

机理：用例第 17 步 `cbuy 0` 真购买（`bal 1000->990:purchased=1`）后，产品按计划 §5「需求 4」进入 **5:00 购买冷却**并关店；其后第 18/19/21–26 步的菜单守卫命令（`cbuy -1/3`、`cdeny`、`cseq`）与第 29 步 `cblock` 真实右键都处在冷却期内 ⇒ 开店被拒。用例写于该规则落地之前，故期望「关店后还能再开」。

已验证的实验性修法（**未入库**）：在第 29 步前插一行 `/astralshop creset CL`（状态归零）后，`CUSE:menu=ChipShopMenu` 转绿；其余 5 条仍红 —— 因为 `cseq0` 期望 `refreshes=2`，归零会变 `3/5`。⇒ 需重排用例（把「无效索引 / 清空负控」放到真购买之前）或改写 `cseq` 前置，属**测试设计改动**，按用户「不处理其他问题」未擅自落地。

## 6. 修复与复验（2026-10-17 深夜；用户裁决「全修」）

### 6.1 修了什么（全部属测试资产，未改产品代码）

1. **`CHIP-LOGIC-{1.20.1,1.21.1}.json`**（两份同源同改）
   - 步骤重排：把「无效索引 `cbuy -1` / `cbuy 3`」与「满包 / 清空负控 `cdeny`」移到**真购买之前**；真购买后紧跟 `cstate`，再插一步 `cinv CL clear`（真购买会在物品栏留 1 枚筹码，不清空会让 `CSEQ0` 的 `inv=0/36`、`CSEQ4` 的 `invDelta=0`、`CSEQ5` 的 `owned=1` 全部读偏），最后 `cprice 0 → cseq`。
   - 两条断言随重排改正：`AP_CL_CBUY:idx=-1/3 …:bal=990->990` → `bal=1000->1000`（购买前余额仍是 1000）。
   - `cblock` 前插 `/astralshop creset CL`：购买会开 5:00 冷却，不清就右键开店被 `CHIP_SHOP_OPEN_DENIED reason=cooldown` 拒绝（`AP_CL_CUSE:res=CONSUME:menu=InventoryMenu`）。
2. **服务端探针 `astral_shop_probe.js`（两线）**：`cseq` 阶段⑤「关店重进」在 `SP_ChipOpener.open(p)` 前加 `ChipShopState.store(p, state.withCooldown(0))`，**只清购买冷却**、保留 `purchased/refreshes/price`。根因：阶段⑤断言 `price=15`，而购买冷却让重开被拒 ⇒ `m5 == null` ⇒ `price=-1`、`CSEQ5OWN` 逐项 `empty`。
3. **`CHIP-ECON-ON-{1.20.1,1.21.1}.json`**
   - 断言保持 `AP_EO_CRECIPES:chips=61:config=1`：**61 是「筹码配方」条数**，池 66 枚里有 5 枚「配方暂缓」（`.121` 提交说明）。此前误按池数改成 66，已改回并实测确认 `chips=61:config=1`。
   - 末段等待 3000 → 6000 ms：`AP_CSC:CTAB` 需客户端探针在「已武装 + 在世界内」满 30 tick 才落盘（每次启动至多一次），3000 ms 会撞竞态（实测 CTAB 晚约 6 s）。
   - note 写明可执行前置：改本线 `run/<ver>/config/astral_dice-common.toml` 的 `enable_chip_recipes = true` → **完整重启客户端** → 跑完改回 `false` 并重启。
