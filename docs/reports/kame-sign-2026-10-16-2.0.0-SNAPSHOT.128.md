## 1. ★ FAIL：一次「自然到期」触发 3 次结算（爱 -12 / 上限 +3）

**判定：FAIL（规格 §3.4 要求单次结算「爱 -4、上限 +1，最高 32」）**

**最小复现（1.21.1，实测）**
```
/gamemode survival @a ; /gamerule naturalRegeneration false ; /gamerule doImmediateRespawn true
/astralkame equip stand "astral_dice:ame_sign" Dev          # 佩戴地雷女立牌
/astralkame set cap 20 Dev ; /astralkame set love 8 Dev     # 起点：爱=8、上限=20
/astralkame poll on                                          # tick 级采样器（love/cap/ovdDur 变化即落一行）
/astralkame ovd Dev 100 0 N1                                 # 施加 100t(=5s) 的 ame_overdose（只替代「施加」这一步）
# 等待 ~5 秒后读数：期望 love=4、cap=21
```
**tick 级证据**（`run/1.21.1/logs/latest.log`，2026-10-16 23:17:00.649 → 23:17:00.893）：
```
AP_POLL:tick=38752:who=Dev:love=8:cap=20:ovdDur=1
AP_POLL:tick=38753:who=Dev:love=4:cap=21:ovdDur=0    <- 第 1 次结算
AP_POLL:tick=38754:who=Dev:love=0:cap=22:ovdDur=0    <- 第 2 次结算（爱 0 已夹逼）
AP_POLL:tick=38755:who=Dev:love=0:cap=23:ovdDur=none <- 第 3 次结算（爱仍夹逼 0，上限仍 +1）
```
**同一现象在 3 个独立臂复现**（1.21.1，均同文件可 grep）：`AP_N1_ST`（21:5x 手动臂，cap 20→23）、`AP_C9_ST`（23:1x，真实主动施加 1200t 后 cap 8→11）、`AP_S4_ST`（23:1x，cap 20→23）。
**跨线复现（1.20.1）**：`run/1.20.1/logs/latest.log`，2026-10-16 23:30:50，同一序列：
```
AP_POLL:tick=1716:who=Dev:love=4:cap=21:ovdDur=0
AP_POLL:tick=1717:who=Dev:love=0:cap=22:ovdDur=0
AP_POLL:tick=1718:who=Dev:love=0:cap=23:ovdDur=none
```
**真实主动路径同样受影响**（不是脚手架特例）：22:5x/23:1x 两个臂用 `BaseSignItem.performSkillForCurio`（= 按键/网络包同路）施加 1200t 的 ame_overdose，63 秒后读数 `love 6→0、cap 8→11`（`AP_C8_ST` → `AP_C9_ST`）。

**机制假设（观察为事实，机制待裁决方确认）**：`event/EffectTimerGuard#tick`（`PlayerTickEvent.Pre`）在「预期已到期而实例仍在表内」时执行 `forceRemove + addEffect(1t)`（源码 `EffectTimerGuard.java:118-127`），NeoForge 的 `tickEffects` 又在派发 `Expired` 之后才移除实例 ⇒ 同一次使用可派发多次 `MobEffectEvent.Expired`；本批 A1 修复移除了 `AmeSignItem#onOverdoseExpired` 里的 `getEffect()!=null` 早退后，这些事件**全部**结算。
**影响**：玩家每次用主动「感情过量摄入」，爱实际 -12（而非 -4）、上限 +3（而非 +1，且更容易撞 32 顶），与 tooltip/手册所写数值不符。
**建议修法方向（未改代码）**：在结算侧做幂等（例如只认「同一实例最后一次 Expired」或以附件记录本次使用的已结算标记），而不是回退 A1 的修复；同时建议顺带审计其它消费 `Expired` 的特性是否也被多次派发。

## 4. 其它观察（登记，不判 FAIL）

1. **全局移除拦截使「奶 / `/effect clear`」对 `astral_dice:*` 效果无效**（既有全局策略，非本批）：`event/ModEffectEvents.java:12-42` 在 `MobEffectEvent.Remove` 上取消非内部移除；实测 `/effect clear Dev`（= `removeAllEffects`，与喝奶同路）后 `ame_overdose` 仍在（`AP_T2_ST`，23:1x）。故规格里「奶/命令清除不触发结算」在本实现下是**因无法清除而天然成立**；主动的**正当退出路径**只有自然到期与卸下立牌。
2. **「摘骰子保留立牌时瞬态修饰器不撤销」**（既有全局口径）：本轮再次观察到 `sign=ame_sign` 且无骰子时 `modL=8` 仍挂（`AP_X0_ST:Bot2`，21:50:58）——只登记，不判 FAIL。
3. **依赖骰子的持续被动**（既有总闸门）：Bot3（戴超天酱、无骰）不获得「一心同体」6 防御（`modK=none`）与指示器镜像重挂；Dev（有骰）则 `modK=12`。符合「立牌一切持续被动需已佩戴骰子」的既有口径，登记。
4. **`kangel_fan` 同 id 复用的 PvP 边界**（待用户裁决项）：本轮未构造 PvP 场景（靶子均用掠夺者），仅登记 `mobs <tag>` 读数里可见「佩戴者自身指示器（amp = 计数-1）」与「目标标记（amp 0）」共用同一 id 的事实。
5. 既有红未纳入本批：`tooltip_color_audit` 64 处、`verify_bountiful_pools` 6 项（交接文档已登记）。

## 7. 工具链问题（本轮实测，供下批参考）

1. **launch 阶段 OP 闸门在一次冷启动里稳定失败**（两条线各 3 次冷启动，全部 `MT_preflight-op: ERROR — 未取到 AP_OP_PERM 读数（注入返回码 /）`）：世界已就绪、模组/探针/清场闸门全 OK，但该闸门注入时（+25~33s）命令未被游戏接收（注入口返回码为空串）。**人工在同一次启动里补注入 `/astralprobe opprobe` 立即成功**（`AP_OP_PERM:has2=1:level=4:src=cmdsource+profile`）⇒ 判为注入时序问题（闸门过早），非产品/探针缺陷；本轮所有用例因此走「手工 launch + 单条 `--phase cases --case`」。
2. `KubeJS server.log 非 0 errors` 的 WARN 亦为本机常态（`server.log` 内实际为 `Loaded 10/10 … with 0 errors`；该 warning 与 `astral_kame_probe.js` 在 1.20.1 上的 KubeJS 包装告警同源，未见功能性影响）。
3. 用例可重复执行需要三件套：`/astralkame mobsreset`（清靶槽位）、`/astralkame resetfans <who>`（清计数**与**目标集；`set fans 0` 只清计数）、显式 `set love/cap`——否则第 2 次执行会与上一轮残留耦合（本轮踩过）。
4. Curios 槽位写入（`setStackInSlot`）**只在真实槽位跃迁时**触发 `onEquip`/`onUnequip`：重复装备同一件不会重放 `onEquip` ⇒ 「装备置 2 层」这类断言必须以**空槽 → 立牌**或显式置层来构造（本轮已改为显式置层，并在用例 note 里登记原始实机证据）。
